% ============================================================== BACKGROUND ==
\needspace{6\baselineskip}
\section{Background and Motivation}

Conventional hospital management systems are administrative record keepers. They store appointments, bills and prescriptions, but they do not manage the part of the visit a patient actually experiences, which is waiting. A patient in an outpatient department cannot reliably learn how long the wait will be, whether the doctor is present at all, or when their turn is approaching, and reception ends up answering these questions by hand, all day.

The clinical side mirrors this gap. A doctor meets a patient with no consolidated view of allergies, chronic conditions, current medications or recent results, and reconstructs that context verbally inside a consultation averaging under ten minutes. Existing products address queueing, clinical documentation and billing in isolation. A unified, cloud-agnostic platform is needed to bring these together without locking patient data into a single vendor.

% ============================================================== PROBLEM ==
\needspace{6\baselineskip}
\section{Problem Statement}

Queue state is invisible to everyone who depends on it, so waiting rooms are managed by calling out a token number rather than by any shared source of truth. Patient context is scattered across visits and departments and is assembled from memory at the moment it matters most, during the consultation itself. At the same time, existing products are either on-premise systems that cannot scale or cloud services that lock patient data into one vendor, which many institutions cannot accept for policy or regulatory reasons. A single platform is needed that keeps the queue synchronised in real time, gives the doctor a consolidated patient view before the consultation begins, and runs on infrastructure the hospital controls.

% =============================================================== OBJECTIVES ==
\needspace{6\baselineskip}
\section{Objectives}

\begin{itemize}
  \item To build a real-time queue keeping the patient's phone, the doctor's workstation and the reception desk on the same state within two seconds of any change.
  \item To generate a consolidated one-page \emph{patient sheet} automatically and deliver it to the doctor before the patient enters the room.
  \item To integrate consultation, prescription, laboratory, billing and pharmacy into one auditable workflow, removing parallel paper records.
  \item To apply AI as a controlled assistant for documentation, report explanation and analytics, under a strict rule that no AI output becomes a clinical record without a clinician's signature.
  \item To enforce privacy by design through role-based access control, per-patient ownership checks and complete audit logging.
  \item To deliver a cloud-agnostic system running unmodified on a managed cloud, a hospital's own Kubernetes cluster or a single server, so patient data never has to leave the institution.
\end{itemize}

% ============================================================== METHODOLOGY ==
\clearpage
\section{Proposed Methodology}

The system is a domain-driven microservice platform. Thirteen bounded contexts are consolidated into eight independently deployable services, because the latency-critical path, from queue to patient sheet to notification, is the one path users watch, and every extra service boundary on it adds a network round trip and a failure mode.

Synchronous HTTP is used only where the caller needs a result to respond, such as a slot availability check. Everything else is an asynchronous domain event over a message broker with per-consumer dead-letter queues and idempotent consumers, since at-least-once redelivery is treated as normal operation rather than an error. Live queue updates reach clients over WebSocket, fanned out through a shared cache so multiple gateway replicas stay consistent, with a polling fallback for unreliable hospital networks.

Each service owns a dedicated database schema and reads no other, giving database-per-service isolation. Patient identity is global while every visit-scoped record carries a hospital identifier, producing true multi-tenancy from the first commit. Clinical facts are never generated by AI; they are retrieved from the owning service at request time through typed, authorization-enforcing tools, and the deterministic patient sheet ships first as the measured baseline any AI-generated sheet must beat before it may replace it.

% =============================================================== TECHNOLOGY ==
\needspace{10\baselineskip}
\section{Technology, Tools and Platforms}

\begin{itemize}
  \item \textbf{Backend} -- Node.js, Fastify, zod, Prisma for validation, serialization and typing from one declaration
  \item \textbf{Data} -- PostgreSQL, Redis and a vector extension for the transactional domain and AI retrieval, without a second datastore
  \item \textbf{Messaging} -- A message broker for routing, retries, dead-letter queues and delayed delivery
  \item \textbf{Object storage} -- An S3-compatible store with presigned URLs, portable to any S3 provider
  \item \textbf{Web} -- Next.js, Tailwind CSS and TanStack Query serving patient, doctor and admin route groups from one application
  \item \textbf{Mobile} -- React Native with Expo, for over-the-air updates without a store review cycle
  \item \textbf{Desktop} -- Electron, for printer and scanner access on reception and pharmacy machines
  \item \textbf{AI layer} -- An orchestration framework against an OpenAI-compatible endpoint, provider-independent and able to run against a self-hosted model
  \item \textbf{Payments} -- A payment gateway behind a provider interface, replaceable by configuration
  \item \textbf{Infrastructure} -- Docker, Kubernetes, Helm and Terraform for one image, one chart and reproducible provisioning
  \item \textbf{Observability} -- A self-hosted metrics, logging and tracing stack, so a customer deployment keeps full visibility
\end{itemize}

% ============================================================ DELIVERABLES ==
\clearpage
\section{Expected Outcomes, Deliverables and Functional Specifications}

The system delivers a patient application, covering OTP registration, discovery with live availability, appointment booking, real-time queue tracking with position and estimated wait, medical records with patient-controlled consent, and prescription and invoice downloads. The doctor workstation provides attendance, priority-ordered queue control, the automatically delivered patient sheet, structured consultation notes, and prescribing with allergy and interaction alerts. Reception and operations get walk-in registration, thermal token printing, queue control with a full audit trail, and a billing and dispensing counter that keeps working through a network outage by queueing writes locally.

The administration console covers hospital, department and fee configuration, staff and role management, and a break-glass workflow that makes clinical content reachable only with a stated reason and a distinct audit record. AI and platform services include a patient sheet agent, a clinical scribe, a triage assistant and a patient copilot, each gated by a human sign-off and an audit trail covering the model, the tool calls and whether the output was accepted or edited. A fully functional prototype demonstrating the complete visit loop, from check-in to signed prescription to invoice, is provided at the end of the project.

% ================================================================== SCOPE ===
\needspace{6\baselineskip}
\section{Project Scope}

The system targets multi-speciality hospitals and clinic chains running outpatient departments, where queue management and clinical documentation are the binding operational constraints. It is deliberately not an inpatient system, a telemedicine platform or an insurance claims processor, and all clinical decisions remain under the control of certified professionals; AI output requires a clinician's signature before it becomes part of the record. The prototype is developed and evaluated using controlled, non-production data to keep the demonstration ethical and safe.

% =================================================================== PLAN ===
\needspace{10\baselineskip}
\section{Project Timeline}

Incremental delivery with a demonstrable workflow at the end of every phase. Verification is a real clinical run rather than a passing test suite.
